Token naming instinct: a blind study of how five AI models name design tokens

We gave five models the same 25 design briefs with no examples, no files and no memory, and asked each one to name 500 things. This report shows what you would actually get back, which names you can trust, and which decisions you still have to make yourself.

The short answer

AI token names are readable and well-formed. They are not stable, and they are not the same across vendors. You can hand the AI the easy half of the job. You still own the hard half.

When this matters

The main use is building a design system for a project that agents will work on, where the aim is to minimise drift: the same thing getting a different name across sessions, pages and models. Drift shows up in three forms. An agent built a page and invented token names as it went, and you need to know which of those names are standard and which are its habit. Agents from more than one vendor read the same system, and their guesses need to land on real tokens. Or you are writing the brief or the instructions for an agent and have to decide what to spell out and what to leave to it. Each takeaway below names the situation it applies to.

  1. An agent built a page and named the tokens itself.Keep the color-role names it chose. color.text.primary, color.action.primary.hover, color.brand.primary and color.link.hover came back identical from all five models, so a different agent later will find them. Replace its typography, spacing and shadow names with your own. Those are the ones it will not repeat next time.
  2. You are writing a design system that agents will read.Write the type scale, the spacing steps and the shadows in full. "A middle spacing step" came back as space-md, spacing.400, space.5 and space.500. Use the standard color-role names and you can skip explaining them. Pick space or spacing, shadow or elevation, typography or font, and list the other as an alias so another vendor's agent still resolves.
  3. You are writing the brief or the instructions for an agent.Describe the product and list its parts: cards, tables, product grid, cart. Do not say "a design system". The two concrete briefs scored about one and a half times the agreement of the generic one, and the generic one even changed which syntax the models wrote in.
  4. You need the same names across sessions, pages or models.Generate once, edit, save the file, and point every later task at that file. Reordering a brief changed nearly half of a model's names. Asking a second model changes more.
  5. You are choosing which model drafts the names.If agents from several vendors will read the result, draft with Opus or Fable. Their names overlap most with everyone else's. If you want one rigid grammar, GPT is the most consistent, especially on typography.

06

Does the brief matter?

Yes, more than the model does. A concrete product gives the AI nouns it can reuse: product, cart, article, KPI. A generic "design system" brief gives it nothing to hold on to, so it falls back on its own habits, and the habits differ.

What to put in the briefName the product and list its parts (cards, tables, product grid, cart drawer). Use plain nouns, not adjectives. If you want a fixed syntax, show one example name. The models do not need a rationale; they need something concrete to attach the name to.
07

Will you get the same names twice?

No. Each brief has 20 items in five groups. We made five versions of every brief by rotating those groups, so the items came in a different order and every line stayed word for word the same. Each model saw all five versions, each in a fresh session. On average a model repeated its own name 54% of the time. For typography, Opus repeated itself only 24% of the time, and Muse repeated any of its names only 46% of the time.

What this means in practiceTreat generated names as a first draft. Run the AI once, edit the result, commit it to a file, and point every later task at that file. Asking a model to "name the tokens again" for a new page will give you a second, slightly different vocabulary.
08

Which model should name your tokens?

None of them is bad at this. They differ in style and in how much their names overlap with everyone else's, which matters if more than one vendor's agent will read your system.

How to choose

  • Agents from several vendors will read the system: use Opus or Fable to draft. Their names overlap most with everyone else's.
  • You want one rigid grammar: GPT. It is the most consistent on typography and never changes syntax.
  • You write CSS directly: Fable already names things as --custom-properties; keep a CSS file as the canonical surface.
  • Whatever you pick: decide space/spacing, shadow/elevation and component-first or property-first up front. These are the three places a different vendor's agent will guess wrong.
09

How to apply this in an agent workflow

For a project where agents build pages against one design system, the aim is to stop names drifting across sessions, pages and models. The findings turn into six habits, in the order a project runs. None of them needs a tool. The first one is worth the most: a thirty-line file removes most of the drift the study found.

  1. Start the project with the file the agent cannot guess.Put the type scale, the spacing steps and the shadows in one short file the agent reads first, before the first session. These are the tokens that drift most: no model names them the same way twice. Decide the three fork words now (space or spacing, shadow or elevation, typography or font), write the one you use, and list the other as an alias. Skip documenting colour roles if they use the standard names; every model produced color.text.primary, color.action.primary.hover, color.brand.primary and color.link.hover without instruction.
  2. When you brief the agent: name the product, not the system.Describe the actual thing ("a storefront with product cards, a cart drawer and a sale badge") and list the parts it will touch. Concrete nouns raised agreement by half compared with "a design system", and the agent reuses those nouns in its token names, which makes them readable to you and to the next agent. Do not say "design system" on its own; that brief produced the worst names and changed the syntax some models wrote in.
  3. Generate names once, at the start, and treat the output as a draft.Keep its colour-role names. Replace its typography, spacing and shadow names with yours from step 1; those are the ones it will not repeat next time. Save the result to a file and point every later task at that file. Do not ask the agent to name the tokens again for a new page: two thirds of names change when the same model is asked twice, and that is where drift begins.
  4. When reviewing agent-written CSS: check the three drift points.Component tokens: button.primary.background or color.button.primary.background? Two models do one, three do the other, so pick a rule and search for the other. State words: they will be last (.hover, .disabled); if your system puts state elsewhere, every agent will get it wrong, so move it. Fork words: spacing where you use space, elevation where you use shadow. These are the most common wrong guesses and the easiest to catch with a search.
  5. When choosing which model drafts: match it to who will work on the project.Agents from several vendors will work on it: draft with Opus or Fable, whose names overlap most with everyone else's. One model will do all the work: GPT drifts least on typography, the only model with a fixed grammar there. You write CSS by hand and want the agent to match: Fable already names tokens as --custom-properties, so keep the CSS file as the source of truth.
  6. When you add a design-system file for agents: write it as aliases, not prose.The mismatches are one word deep, so a short alias table resolves more of them than any explanation. An agent that guesses color.text.muted then lands on a real token instead of inventing one.
The one-line versionLet the agent name what every model already agrees on, write down what no model agrees on, say what the product is, and never generate twice. That is what keeps a project's token names from drifting.

Method and limits

Design

Five briefs: a SaaS analytics dashboard, an editorial site, an ecommerce store, a professional-services marketing site, and a generic website design system. Each brief lists 20 tokens to name, in five groups of four: color primitives, color roles, typography, spacing and shape, and component tokens. Five versions of each brief rotate the group order so every group sits in every position once. Each of the 25 prompts went once to each of the five models in a fresh Cursor subagent with no tools, no files and no memory. Models were asked for JSON only and no explanation, so the instruction itself would not change the naming behaviour. Model identities were hidden during review.

Counting agreement

Raw names are kept as returned. To compare across syntaxes, names are split on dots, dashes, underscores and camelCase, lowercased, and the -- prefix is dropped. Synonyms are never merged: spacing and space count as different words. "Agree" means the same words in the same order.

Integrity

  • 125 of 125 runs completed. Every transcript shows zero tool calls. The fifth model, Muse Spark 1.3, was added after the first four on the same frozen prompts; the earlier runs were not touched.
  • 121 runs passed the strict JSON contract. The four failures were GPT runs that added commentary after valid JSON; the JSON was used unmodified and the failures are still counted as failures.
  • Reordering the brief had a small effect on agreement (46% to 55% majority by position) and no group of tokens was tied to one position, so the per-kind results are not an ordering artifact.

Limits

  • One sample per prompt per model at Cursor's default settings. Per-token figures rest on five comparisons per pair of models and are evidence, not estimates.
  • The 2,500 names come from 125 runs and are not independent observations.
  • Strict JSON may suppress some natural naming behaviour.
  • Results describe these five Cursor model configurations on 13 October 2026, not every model from each vendor.
